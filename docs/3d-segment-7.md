# Segment 7: 3D construction quizzes and final audit

Segment 7 completes the shared 2D/3D DGS with mathematical 3D construction quizzes. The implementation extends the existing LiaScript quiz bridge, board lifecycle, scene registries, DGS restore path, localization, and accessibility conventions. It does not create a second renderer or copy a solution into the learner board.

## Architecture

A quiz check follows one bounded pipeline:

1. `quiz3dTypes.ts` parses and validates the author definition.
2. `constructionQuiz3d.ts` reads the current shared 2D/3D scene without mutating it.
3. Board objects become camera-independent canonical objects. Existing 2D geometry is promoted with `z=0`.
4. `quiz3dGeometry.ts` builds type-filtered candidates and finds a unique weighted matching. One learner object cannot satisfy two targets.
5. In `result` mode the mathematical result is compared. In `construction` mode the dependencies and intrinsic parameters are compared as well.
6. Conditions and measurements are evaluated with the same central tolerance model.
7. The structured result is localized and passed to the existing LiaScript quiz input. Feedback is exposed through an accessible `role=status` live region.
8. Reset, host removal, board replacement, and remount use the normal DGS and quiz lifecycle cleanup.

JSXGraph objects are adapters only. IDs generated by JSXGraph, DOM order, the projection, camera position, and visible sampling points are never grading inputs. Renderer helpers are removed before matching. A reference answer is represented by the declarative `expected` objects and `conditions`; therefore checking needs no permanent hidden reference board, renderer, listener, observer, or timer.

## Macros

The English and German names are equivalent:

- `@ConstructionQuiz3D` / `@Konstruktionsquiz3D`
- `@CombinedConstructionQuiz3D` / `@KombiniertesKonstruktionsquiz3D`

All four macros use the existing LiaScript check, hint, and solution body. The first argument is either compact syntax or a JSON object. The second argument is the usual LiaScript quiz option comment.

```lia
@CoordinateSystem(`xmin=-3;xmax=3;ymin=-3;ymax=3;zmin=-3;zmax=3;mode=3d;width=520;id=raum_quiz`)
@DGS(`raum_quiz`)

@Konstruktionsquiz3D(`raum_quiz;mode=construction;view=3d;objects=[{"id":"P","kind":"point3d","point":[1,1,1]}];versuche=3`,`<!-- data-hint-button="1" data-solution-button="2" -->`)
[[?]] Konstruiere den Punkt $P(1|1|1)$.
*****************
Nutze das Punktwerkzeug in der räumlichen Ansicht.
*****************
```

JSON is preferable for larger definitions:

```json
{
  "boardId": "raum_quiz",
  "mode": "construction",
  "viewPolicy": "free",
  "liveFeedback": false,
  "maxAttempts": 3,
  "allowAuxiliary": true,
  "forbidExtra": false,
  "includeAuthored": false,
  "expected": [
    {
      "id": "P",
      "kind": "point3d",
      "point": [0.5403023059, 0.8414709848, 0.3333333333],
      "dependency": {
        "definition": "point-on-object",
        "boundTo": "curve-c",
        "bindingKind": "curve",
        "dependent": true,
        "parameters": { "kind": "curve", "t": 1 }
      }
    }
  ],
  "conditions": []
}
```

Compact aliases include `modus`, `objekte`, `bedingungen`, `toleranz`, `hilfsobjekte`, `zusatzobjekteverbieten`, `namenrelevant`, `sichtbarkeitrelevant`, `fixierungrelevant`, `formatierungrelevant`, `reihenfolgerelevant`, `vorgabenbewerten`, `ansicht`, `versuche`, `hinweise`, and `loesung`. Boolean values accept the project-wide boolean syntax. `viewPolicy`/`view` is `free`, `2d`, or `3d`. A locked view policy disables the disallowed 2D/3D switch but leaves camera, projection, zoom, panning, selection, Undo/Redo, object list, properties, sliders, and DGS tools usable.

## Modes and policies

`mode=result` accepts any construction with equivalent final geometry. Examples include a line with another support point, a plane made from other valid sources, or a circle created through three points rather than center and radius.

`mode=construction` first requires equivalent geometry and then checks the requested dependency data. Supported dependency fields are `definition`, `sourceIds`, `referenceIds`, `driverIds`, `tracePointId`, `boundTo`, `bindingKind`, `transformation`, `dependent`, and nested `parameters`. `dependencyAlternatives` permits several accepted construction routes. Nested numeric parameters use the scalar tolerance instead of exact floating-point equality.

Auxiliary objects are allowed by default. `forbidExtra=true` rejects unmatched non-auxiliary learner objects. `includeAuthored=false` prevents pre-authored task objects from satisfying the answer. Names, visibility, fixed state, formatting, order, and polygon orientation become grading inputs only when their corresponding option is enabled.

Three independent segments that form a closed triangle are also exposed as one synthetic polygon candidate. Their endpoints may be different point instances at equal coordinates. The three component segments are not then counted again as forbidden extras.

## Supported canonical objects

| Kind | Relevant canonical data |
|---|---|
| `point3d` | coordinates; optional binding, intersection, projection, or transform dependency |
| `vector3d` | components and orientation; an anchor is optional for a free vector |
| `segment3d` | unordered endpoints and finite domain |
| `line3d` | support line; support point and direction scaling/sign are representation-independent |
| `ray3d` | origin and oriented half-line |
| `plane3d` | support point/normal or equivalent plane coefficients |
| `circle3d` | center, radius, carrier-plane normal up to sign |
| `sphere3d` | center and radius |
| `polygon3d` | cyclic vertex set; reversed order is accepted unless orientation is relevant |
| `solid3d` | tetrahedron, pyramid, prism, parallelepiped, cuboid, cylinder, cone and their defining geometry |
| `curve3d` | definition and interval, or bounded bidirectional geometric equivalence |
| `surface3d` | definition and both parameter ranges, or bounded geometric equivalence |
| `conic3d` | conic classification, plane/frame, center/vertex/axes/radii/branches and sources when requested |
| `scalar3d` | finite analytic or measurement value |

The adapter recognizes ordinary 2D points, vectors, segments, lines, rays, circles, polygons, functions, regression/drawing curves, families, analysis objects, and their 3D registry equivalents. See [the final object/function matrix](3d-object-function-matrix.md) for macro, DGS, roundtrip, quiz, and lifecycle evidence.

## Conditions and measurements

A definition can combine expected objects with weighted conditions:

```json
{
  "conditions": [
    { "kind": "incidence", "objects": ["P", "g"] },
    { "kind": "parallel", "objects": ["g", "h"] },
    { "kind": "orthogonal", "objects": ["g", "k"] },
    { "kind": "relation", "objects": ["g", "h"], "relation": "windschief" },
    { "kind": "distance", "objects": ["P", "E"], "value": 2 },
    { "kind": "angle", "objects": ["g", "E"], "value": 90 },
    { "kind": "measurement", "objects": ["S"], "measurement": "radius", "value": 2 }
  ]
}
```

`relation` supports the shared spatial relation vocabulary, including identical, intersecting, truly parallel, contained, and skew relations in German and English. Angles in condition definitions use degrees by default; set `unit: "rad"` / `einheit: "rad"` explicitly for radians. A condition-specific angle tolerance uses the same authored unit and is normalized internally to radians. The internal vector operations normalize directions before comparison. Scalars use absolute and relative tolerances.

## Tolerance model

Defaults are centralized in `DEFAULT_QUIZ_TOLERANCE_3D`:

| Quantity | Default |
|---|---:|
| coordinate | `1e-5` |
| angle | `π/720` rad (`0.25°`) |
| absolute scalar | `1e-6` |
| relative scalar | `1e-5` |
| incidence | `1e-6` |
| parallel | `1e-6` |
| orthogonal | `1e-6` |
| curve | `2e-3` |
| surface | `4e-3` |

Coordinate and measurement comparisons scale with the magnitude of their inputs. Direction tests use normalized vectors and reject degenerate norms. Non-finite values never pass. Authors can override individual keys with `tolerance`/`toleranz`; invalid or negative values are author errors.

## Feedback, hints, solution, and reset

The evaluator returns `correct`, `partial`, `incorrect`, or `author-error`, a weighted score, unique object matches, and structured issues such as missing object, wrong type, position, size, value, dependency, condition, forbidden extra object, degenerate geometry, or undefined result. Learner-facing German and English feedback avoids internal object keys. Configuration problems are reported as technical author errors and do not count as a wrong learner construction.

Hints and solutions remain LiaScript content after the macro's quiz separator. They are rendered by the existing LiaScript runtime and never insert answer objects into the learner board. The added Reset/Zurücksetzen button is keyboard accessible, restores the initial DGS snapshot, clears the local attempt/result/feedback state, and rebinds to a replacement board with the same ID. `maxAttempts` is enforced by the bridge. Optional live feedback listens only to relevant geometry changes and is debounced; camera-only changes do not trigger a check.

## Combined 2D/3D tasks

The combined macro and normal 3D macro share the same implementation. A 2D object is canonicalized with `z=0`, while a real 3D object keeps its coordinates and identity. Switching views changes only the presentation. Camera and parallel/central projection do not change a score. An author may require `2d`, require `3d`, or permit `free` switching.

## Validation and troubleshooting

Parsing rejects a missing board ID, empty task, unknown object or condition kind, duplicate expected IDs, references to unknown condition targets, invalid or negative tolerances, invalid attempt counts, non-finite/incomplete geometry, zero directions, and cycles among expected dependencies. The browser then distinguishes a valid definition whose board is temporarily absent from an invalid definition.

For a geometrically correct answer that fails in construction mode, inspect the source IDs, binding kind, transformation type, and intrinsic `parameters`. Use `dependencyAlternatives` when several source constructions are intentionally accepted. For unexpected extra-object errors, mark helpers as auxiliary or disable `forbidExtra`. Set `includeAuthored=true` only for tests or tasks where a prebuilt object is intentionally part of the learner answer.

## Roundtrip and lifecycle audit

The quiz definition is course content. Geometry remains in the existing DGS export/import format. Segment 6 and the final audit exercise macro creation, DGS-created objects, transformed and dependent objects, export, fresh import, canonical re-export, Undo/Redo, 2D/3D switching, cleanup, and remount. Missing source references are isolated so that the remainder of an import can still load.

The board cleanup path removes quiz listeners, actions, feedback elements, pending debounces, and stale board references. Board replacement and Shadow-DOM remount bind exactly one action set. No solution renderer or hidden reference scene is kept alive between checks.

## Performance and numeric limits

Matching filters by canonical kind and dimension before doing geometric comparison, never reuses a learner object, and bounds candidate work. Curve comparison uses bounded adaptive samples plus a bidirectional nearest-point test. Surface comparison uses a bounded `7 × 7` grid and bounded nearest-parameter search. General symbolic equivalence of arbitrary curves and surfaces is outside the scope. Authors can request exact normalized definitions with `parameterizationRelevant=true`.

Synthetic triangle recognition inspects at most 32 segment candidates per check. Sampling, numerical searches, dependency traversal, and matching do not create global polling loops or per-object timers.

On the deliberately large Segment-6/7 browser fixture, a warmed check took approximately 8–72 ms; its cold first check took about 6.4 s and a full initial-snapshot reset about 32 s because that reset rebuilds the complete stress scene. The normal dynamic 2D interaction profile reported zero long tasks and action p95 values around 2–2.9 ms. These measurements are machine/runtime dependent and are retained as regression evidence rather than product promises.

## Known boundaries

- Arbitrary curve and surface equality is numeric and bounded, not a symbolic proof.
- Synthetic recognition currently combines three independent sides into a triangle; arbitrary n-gons should be authored as polygon objects.
- Appearance checks cover the shared color, opacity, width, visibility, and fixed metadata available in canonical adapters.
- A resolved native LiaScript quiz remains governed by LiaScript's own solved-state UI. The DGS reset restores the construction and local feedback state.
- The standalone external freeze adapter still reports point hydration as unavailable, while full DGS restore hydrates the point correctly.
- The external freeze/integration layout adapter restores the set-square pivot with a small measured ratio drift. In the final run, standalone integration expected about `(0.439214, 0.113929)` and restored `(0.436020, 0.113100)`; the full-DGS path expected `(0.408164, 0.102676)` and restored `(0.405196, 0.101929)`. Point and bounding-box state remain correct in the full-DGS path. These cases stay marked `passed-with-adapter-limitation` in the performance artifact.
